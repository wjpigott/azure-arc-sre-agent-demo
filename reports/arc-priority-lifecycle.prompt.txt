Create or reconcile a read-only Live Report named "<resolved-report-name>"
using the Arc Priority & Lifecycle blueprint. Resolve the approved agent,
subscription, Arc resource groups, workspace and inventory Computer aliases
from config/live-report-catalog.json for this deployment. Do not create a
report with unresolved scope placeholders. Reuse an existing report only after
verifying its name, agent and scope; DEV/TEST reports must not overwrite
production reports.

Query the selected Azure scope using approved Azure resource read / Resource
Graph tools, and query the selected workspace using Monitor Workspace Log
Query. Authenticate to the tenant containing each queried subscription.
Never embed old Azure resource inventory as if it were a live source.
Filter workspace rows to the approved machine scope and show ambiguous
resource-to-Computer mappings as NeedsReview rather than joining unrelated
machines by an assumed hostname match.

Preserve the following layout:

Summary cards: distinct scoped machines, connected, planned offline, unexpected
disconnected, critical/high/warning findings and source-data gaps. Label
machine counts separately from finding counts. Do not assume a previous
maintenance run targeted the same number of machines as today's fleet.

1. Priority Action Queue: severity, machine, condition, evidence/source,
observation timestamp, likely cause, confidence and recommended next action.
Rank verified findings first. Treat likely cause as a hypothesis unless
supported by evidence. Separate planned-offline conditions and approved
exceptions from actionable failures.

2. Patch & Maintenance Readiness: live Update Manager assessment status,
critical/security/definition counts, reboot debt and assessment time;
maintenance configuration, schedule, duration and target scope; current and
previous run status, message and timestamps. Missing, failed or stale
assessments are explicit states, not zero missing patches.

3. Lifecycle & Currency: Arc Connected Machine agent versions and approved
release rings; AMA/extension versions and failed provisioning; Azure Arc SQL
instance version/edition and lifecycle; Windows/Linux support posture.
Use config/arc-agent-baseline.json, config/arc-agent-exceptions.json and
config/arc-extension-baseline.json after reviewing their sources and dates.
Honor time-bound exceptions and approved release lag. Never hardcode a
snapshot's "latest" release or mark every nonmatching version outdated.
If baseline review or version parsing is insufficient, report NeedsReview.
Verify OS/SQL support dates and ESU entitlement separately; do not infer an
active ESU license from an old SKU label or extension presence.

4. Performance & Capacity: OS disks below 15% free, CPU average above 70%,
and memory pressure under an explicitly reviewed memory policy. Show the
measurement window, counter, average and minimum/peak, and require sustained
evidence rather than one isolated sample. Make thresholds configurable and
visible. A missing counter or unconfigured memory threshold is a data/policy
gap, not a healthy result.

5. Reliability & Configuration: Windows critical/error events and Linux
high-severity syslog over 48 hours; repeated service/extension failures;
Change Tracking changes over seven days; telemetry coverage gaps using Arc
connection state and fresh Heartbeat/Perf/Event/Syslog evidence. Group repeated
symptoms without losing counts, source timestamps and representative evidence.
No recent events alone does not prove missing collection. A connected Arc
machine without telemetry requires diagnosis of collection, scope, permissions
and ingestion; do not assert that a specific extension is missing without
resource evidence.

Use queries/telemetry-ingestion.kql as a workspace-level ingestion diagnostic,
not proof of every machine's telemetry coverage. VM Application assignment
context can use queries/arc-vm-applications.arg after applying the approved
scope. Those files are supporting queries, not the complete report definition.
The exported HTML does not contain the original live queries: author and
validate the remaining section queries against the available schema/tools.

Every section must show source retrieval time, observation time and freshness.
A freshly rendered header must not hide month-old resource or maintenance
evidence. Show historical run times as history, not current failures without
validation. On reload use current approved connector reads and state any
cache. Errors, missing tables/tools, no data, truncation and stale sources must
remain visible. Never substitute a previous snapshot or invent support dates,
machine counts or recommendations when a source fails.

Do not include write-action buttons or call remediation tools. Do not patch,
reboot, upgrade agents/extensions, deploy applications, change maintenance,
run guest commands or grant permissions. Save the report and return its ID,
scope, query/source validation results and unresolved gaps as private
deployment output. Do not report creation success until the saved report
can be opened and its approved read tools verified.
